## 1. What the game is

A mobile puzzle game where arithmetic is drawn with **seven-segment matchsticks**.
The player is shown an equation with segments missing and must tap segments to
form digits that make the equation true.

```
   ┌─┐       ┌─┐
   │ │  ...  │ │      ← tap segments to build each digit
   ├─┤   +   ├─┤
   │ │       │ │
   └─┘       └─┘
   ─────────────
      answer
```

Two modes:

| Mode | Shape | Cost | Purpose |
|---|---|---|---|
| **TRAINING** | Single player, endless streak, own difficulty pick | Free forever | Learning, practice, the guaranteed fallback |
| **ARCADE 1v1** | Real-time race, first-to-N rounds | Entry fee in coins | Competition, rating, retention |

**The 1v1 rule:** both players get the *same* equation at the same moment. The
round ends the instant either one answers correctly. There is **no time limit** —
it is a race, not a countdown. Both players are then shown the correct answer.
If both submit wrong/timeout, the round is redone with no winner.

### Puzzle shapes by difficulty (verified in `GameManager`)

| Mode | Equation | Digits | Operators |
|---|---|---|---|
| Easy | `A ± B = C` | 2-digit | one |
| Medium | `A ± B = C` | **3-digit** | one |
| Hard | `A op₁ B op₂ C = D` | 2-digit | **two independent** |

Every generated puzzle is checked to have **exactly one** (digits, operators)
solution — the generator retries up to 200 times until uniqueness holds.
An arcade mode selector also offers **RANDOM battle** (`GameMode.Random`),
which resolves to a concrete difficulty when the match starts and is charged
at the Medium entry fee.

### Training timers (verified in `TimerManager`)

Training is a countdown: **100 / 200 / 320 s** (Easy/Medium/Hard). The original
30/60/90 predated Medium growing to three digits and Hard to two operators; the
interim 50/100/160 was doubled again after play-testing — reading a
seven-segment puzzle is slow work, and a clock that runs out mid-thought
teaches nothing. Each win tightens the clock by 3 s down to a floor of 65% of
the start time; a loss resets it. The readout shows **M:SS above a minute and
SS:CC below it** (the old `seconds % 100` wrapped: a 100-second round opened
reading "00:00"). Arcade rounds run a count-up stopwatch instead (`max = 0`
signals "no limit" to the HUD).

## 3. The one convention that governs everything

> **The entire UI is generated by an Editor script. Do not edit the scene by hand.**

`Assets/Editor/SceneBuilder.cs` (~3,200 lines) builds every panel, button, label
and sprite procedurally and saves `Assets/Scenes/MainScene.unity`.

**To apply any UI change: Unity menu → `PlusMinus` → `Build Scene`.**

Consequences that trip people up:

- Hand-edits to the scene are destroyed on the next build.
- Sprites are generated in code (`MakeRoundRect`, `MakeCircle`, `MakeSoftDot`,
  `MakeRing`, `MakeSpeakerCone`, `MakeSlash`, `MakeVerticalGrade`, `MakeVignette`).
  There are **no external art assets** (the two fonts in §4 are the sole
  exception).
- Button clicks are wired with `UnityEventTools.AddPersistentListener` at build
  time, so handler methods must be `public void` with no arguments.
- **If a script renames a public member, the scene silently keeps the old
  serialized reference** — always re-run Build Scene after refactoring.
- A stale scene plus new scripts is the single most common source of confusing
  runtime errors in this project.

### Canvas geometry — the number everyone gets wrong

`CanvasScaler` reference is **1080×1920** with `matchWidthOrHeight = 0.5`, which
is a *log-weighted* lerp:

```
scale  = 2^lerp(log2(1080/1080), log2(2340/1920), 0.5) = 1.10398
canvas = 1080/1.10398 × 2340/1.10398 = 978 × 2120 reference px
```

**On a real phone the canvas is 978 px wide, not 1080.** Content wider than
~880 px has under 50 px of margin. This has already caused real bugs.

### Anchoring rule

> Two elements whose spatial relationship carries meaning must be anchored to the
> same edge.

Mixing top-, centre- and bottom-anchored children in one vertical stack makes the
group drift apart by ~100 px per anchor boundary on a tall phone. Children of a
**fixed-size parent** (cards, list rows) are exempt — they cannot drift.

## 4. Architecture

`Assets/Scripts/` — **~9,900 lines across 45 runtime scripts** (the dead
`DebugOrientationDisplay` was deleted in the 2026-08-21 pass), plus
`Assets/Editor/` with 3 scripts (`SceneBuilder`, `SceneBootstrap`,
`AndroidBuildSetup`). Singletons, wired by `SceneBuilder` onto one `Managers`
GameObject. Firebase's own bundled sources add ~500 lines outside `Scripts/`.

Fonts are the only external assets: **DSEG7 Classic Bold** (the seven-segment
display face) and **Orbitron Bold**. Everything sprite-shaped is still generated
in code (§3) — and so is every *sound*: the heartbeat and the tutorial click are
synthesized sample-by-sample at runtime.

## 5. Firebase data model

```
users/{uid}            displayName, online, lastSeen
presence/{uid}         true (onDisconnect removes)
matchmaking/{uid}      displayName, timestamp, mode, firstTo
                       — or, once claimed: matchId, hostUid   (the handshake, §6)
matches/{id}           hostUid, players{}, settings{}, scores{}, rounds{}, state,
                       winner, currentRound, rematch{}, nextMatchId
invites/{uid}/{id}     fromUid, fromName, mode, firstTo, timestamp, status, matchId
friends/{uid}/{fid}    displayName
stats/{uid}            elo, wins, losses, matches, currentStreak, bestStreak,
                       roundsWon, roundsLost, coins, country, displayName, updatedAt
daily/{uid}            streak, longestStreak, lastLoginDate, streakClaimedDate,
                       challengeDate, challenges{ i: type, target, progress, claimed }
leaderboard/global/{yyyy-MM}/{uid}         name, elo, wins, country
leaderboard/country/{CC}/{yyyy-MM}/{uid}   same
```

**The rules live in the repo** at `firebase-database-rules.json` — **v2**
(2026-08-21), written against three verified constraints:

1. **Stats and daily are saved with `UpdateChildrenAsync`** — a multi-location
   update where each child path validates alone and sibling values are not
   visible to each other. Every rule stands alone; the v1 rule
   `wins <= parent.matches` would have rejected the very first save of a brand
   new account.
2. **The queue claim is a transaction scoped to `matchmaking/{oppUid}` only**
   (§6), so no matchmaking-root `.write` is granted — v1's committed shape
   would have denied the old root transaction the moment it was published.
3. **The leaderboard row validates against `root.stats/{uid}/elo`.** It is
   written right after the stats update on the same connection, so the server
   has already applied the new elo. A row elo that doesn't match is a forgery
   and dies — this is what actually closes the "fake Master" hole; v1 only
   bounded the number.

Beyond that: creation is pinned to the game's real starting state (elo == 1000,
coins == 0, counters == 0), per-write deltas bound elo (±60) and coins (+300),
career counters are monotonic, invites must be signed with the sender's own uid,
friends writes are legal only for the two people in the pair, matches can only
be created *by a player in them*, and `.indexOn: "elo"` sits on every
leaderboard month node (without it Firebase downloads every row to the phone
and sorts locally, burning the free-tier quota).

**Trust model:** the client writes `stats/{uid}` directly; the rules are the
entire defense. Publish v2 wholesale from the console (the rules parser accepts
`//` comments).

## 6. Match flow (1v1)

```
RANDOM BATTLE
   → pay entry fee
   → enter matchmaking queue (matchmaking/{uid} = name, mode, firstTo, timestamp)
   → poll ~1.0–1.3 s:
        · my own entry now holds {matchId, hostUid}?  → I was CLAIMED:
          delete my entry, join that match                      ← the handshake
        · a compatible entry exists? → CAS-claim IT:
          transaction on matchmaking/{oppUid} alone —
          abort if gone, else overwrite with {matchId, hostUid}
          (the match id is minted client-side BEFORE the claim);
          on success: delete own entry, create matches/{matchId}
   → 5 s without a human?  →  BotMatchManager takes over (player is not told)
   → host generates the equation and writes it to Firebase
   → both clients render the same puzzle
   → first correct answer ends the round        ← no timer
   → both see "CORRECT ANSWER: 27 + 41 = 68"
   → first to N rounds wins the match
   → ELO + coins settle
   → REMATCH is negotiated through rematch{} on the finished match node
```

**History note (fixed 2026-08-21):** the original claim was a transaction on the
matchmaking *root* that deleted both entries. That had two fatal problems: the
claimed side was never told the match id (its entry just vanished, it kept
polling an empty queue, and the bot fallback quietly swallowed every real 1v1
pairing ~5 s later), and a root transaction needs a root-level `.write` no sane
ruleset grants. The claim now *writes the match id into the claimed player's
entry*; discovery of that id is the handshake. Known residue: a
milliseconds-wide window where two hosts claim each other simultaneously can
strand one in a WAITING screen — the Cancel button refunds and exits; revisit
with real traffic (§10).

**Round arbitration** is host-side: `ArcadeMatchManager.WatchForFirstCorrect()`
polls the answers node from the moment the round opens and settles on the first
`correct == true`. It must start at round open, not after the host answers —
otherwise a host who never solves deadlocks the round.

**Bots are not disclosed to the player.** Half use the exact guest name shape
(`Player_48213`), half use handle+suffix names. Bot strength maps the player's
ELO through `InverseLerp(800, 1800)` plus a ±0.18 per-match wobble; solve time
per round is drawn between 30% and 115% of a difficulty-nominal time
(30/45/60 s), so the bot *always* answers eventually — an unsolvable round
still ends, and beating the bot means being faster. This is standard
practice, but it is a deliberate choice and should be revisited if the player
base ever becomes large enough that it is unnecessary.

## 7. Design decisions worth preserving

Each of these was a real problem with a non-obvious fix.

**The operator has no invalid state.** It used to be two independently tappable
sticks: four physical states for two meanings, where "neither lit" and "only
vertical lit" could never be correct and `CheckAnswer` failed *silently*. In Hard,
12 of 16 combinations were dead. It is now a single key that toggles between −
and +, framed like every other button so it reads as one control.

**Ranked difficulty is symmetric.** The rating swing is weighted **×0.75 Easy /
×1.0 Medium / ×1.25 Hard** on wins *and* losses alike (`RankWeight`), and every
match moves the rating by at least ±1. A win-only bonus is the obvious reading
of "harder should pay more", but it inflates the ladder until rating means
nothing. **Difficulty is paid in coins, not rating** — coins have no ladder to
distort. Ranks are six tiers with floors at 0 / 1000 / 1150 / 1300 / 1450 /
1600 (Bronze → Master); a new account starts at 1000, on the Silver floor.

**Bot matches move rating at half K (16 vs 32).** They still count, but they
cannot carry someone up the leaderboard.

**Dates come from the server**, never the device
(`FirebaseDBManager.ServerDateKey`). Streaks cannot be farmed by changing the phone
clock.

**A failed read is not an empty account.** Both `PlayerStatsManager.Load()` and
`DailyManager.Load()` return early on a faulted read instead of saving defaults
over a real record. This was a live data-loss bug.

**Training is free forever.** This is the anti-lockout guarantee. Everything else
in the economy is built on it.

## 8. Economy

### Current constants (verified in code)

| Thing | Value | Where |
|---|---|---|
| Starting balance (new account) | **0 — START_COINS (100) is paid on the first *finished* match** | `PlayerStatsManager.ApplyResult` (`Matches == 1`) |
| Login bonus | `50 + 10×(streak−1)`, cap **150** (day 11) | `DailyManager.StreakReward` |
| Daily challenges | 3/day, 15–40 each (PlayMatches / WinMatches / WinRounds / WinOnHard) | `DailyManager.POOL` |
| Win payout | **10 / 18 / 30** (Easy/Med/Hard) | `PlayerStatsManager.WinCoins` |
| Entry fee | **3 / 5 / 9** (Random battle charged at Medium) | `PlayerStatsManager.EntryFee` |
| New-player shield | ranked entry **free while `Matches < 25`** | `PlayerStatsManager.SHIELD_MATCHES` |
| Free ranked entries when broke | **3 / day** | `PlayerStatsManager.FREE_ENTRIES_PER_DAY` |
| Rewarded ad | **30** (kept below the 50-coin day-1 login bonus) | `ArcadeGUIManager.AD_REWARD` |
| Ad daily cap | 5 | `AdManager.dailyCap` |

Entry-fee handling is defensive end-to-end: `TryPayEntry` records a
`pendingFee`, **every error path refunds it** (`ShowError → RefundEntry`), and
it is only zeroed once a match genuinely starts.

**Fresh-account arbitrage is closed.** `Load()` no longer pays anything on
sight; a brand-new row is created at 0 coins and `START_COINS` lands exactly
once, when `Matches` ticks to 1 — the DB rules pin creation to `coins == 0` and
bound every subsequent write's delta, so the closure holds server-side too.
The shield still makes the first 25 ranked matches free, so a new player is
never locked out while broke.

One accepted weakness: the free-entry counter and the ad daily cap live in
**PlayerPrefs (device-local)**, keyed to the server date — a reinstall resets
them. Cheap to exploit, cheap to ignore at zero players.

### Why the fees are 3 / 5 / 9 (the audit that forced the change)

The first version used 5/8/12 against payouts of 10/18/30. Break-even win rate
is `fee / payout`, which put Easy at 5/10 = **50.0%** — *exactly* the
equilibrium win rate that ELO matchmaking (and the ELO-tracking bot) drives
every player toward. Expected drift there is exactly zero, and a zero-drift
random walk against an absorbing barrier at zero reaches zero with
probability 1. Over 100 Easy matches, **46% of players ended below where they
started** — and Easy is where weaker players live, so the old ladder punished
exactly the people who most needed to keep playing.

| Mode | Fee | Break-even | Drift at 50% WR |
|---|---|---|---|
| Easy | 3 | 30.0% | +2.0 |
| Medium | 5 | 27.8% | +4.0 |
| Hard | 9 | 30.0% | +6.0 |

Every mode now sits near a 30% break-even, an even win rate drifts upward
everywhere, and dropping to Easy after a slump is a real recovery. This
reasoning is preserved verbatim as comments in `PlayerStatsManager` — keep it
there.

### The real sink is cosmetics, not entry fees

An entry fee creates tension; it cannot be the economy. `ColorManager` and
`GameSettings` already hold **8 segment colours and 8 background colours, all
free**. Pricing them (leave 2 of each free; ~400–500 per colour, ~1,500 per theme)
turns every coin already being earned into progression, and needs no gate at all.
This is the intended long-term sink and it is greenfield.

### Anti-lockout invariant

> A player can always play, and can always earn coins, without spending money.

Enforced by: Training is free and unlimited (`OnPlayTrainingPressed` on the
out-of-coins sheet); the login bonus arrives regardless of play; the new-player
shield and the 3 daily free entries extend the guarantee to ranked play; and
the out-of-coins sheet never hides its free exit even when no ad can be served.

## 9. Ads

`AdManager` is the only seam. **No ad SDK is installed.**

It ships a **stub** so the whole flow is testable today, with two guards against
shipping it:

1. Without the `MATHSTICK_ADS_ADMOB` compile symbol it logs a loud warning on
   every use.
2. In a **non-development build** without the SDK, `IsRewardedReady` returns
   `false` — a released APK with no SDK pays out nothing.

**Contract:** `ShowRewarded(Action<bool>)` calls back `true` **only** on a
completed view. Rewarding a dismissal violates every ad network's policy and gets
accounts suspended.

**To go live:** install the Google Mobile Ads Unity plugin, define
`MATHSTICK_ADS_ADMOB`, and fill in `InitialiseReal` / `IsRealAdLoaded` /
`ShowReal`. Use Google's public **test** ad unit IDs during development — never
click live ads on your own account.

The pause-presence interaction is already guarded: `AdManager.IsShowing` makes
`FirebaseDBManager.OnApplicationPause` a no-op while an ad is on screen, so a
fullscreen ad can no longer remove the presence node and trip the opponent's
15-second disconnect forfeit.

**Best placement for revenue is not the out-of-coins gate** — with ~150 coins/day
of passive income it will fire for almost nobody. It is a **"double your match
reward"** button on the result screen: opt-in, post-win, emotionally free.

## 11. Business model

**Free to play, ad-supported, cosmetics-monetised.**

| Line | Model |
|---|---|
| Rewarded video | Primary. ~$5–15 eCPM. Opt-in only. |
| Cosmetics | Coins earned in play; optional IAP later. **Never pay-to-win** — advantage-for-money in a maths game kills it. |
| Interstitials | Deliberately absent. Would break the 1v1 race. |

**Costs:** Firebase Spark **free** (100 concurrent connections, 1 GB, 10 GB/month
egress). Google Play developer account **$25 one-time**. AdMob free. The main
cost risk is crossing Spark's connection limit, which is a good problem.

**Because the game may read as child-directed** (it is a maths puzzle), Google
Play families policy and COPPA affect ad personalisation and therefore eCPM. This
must be resolved before monetising. **It also touches Auth, not just ads:** if
the app is declared child-directed, Google/Facebook sign-in for minors becomes a
policy question in its own right. Decide the audience declaration early.

**Retention design**, in the order it was built and in order of impact:
bot fallback (without it matchmaking dead-ends at zero players) → rematch
(multiplies session length) → stats/ELO/ranks (the number that goes up) → monthly
leaderboards, which **reset** so nobody faces an unreachable all-time top ten →
daily login streak → daily challenges.

**Checklist before believing a UI bug:**

   common cause of confusing failures.

rules parser accepts the `//` comments in the file. Publish v2 *together with*
(or before) shipping a build containing the 2026-08-21 `LobbyManager` claim —
the old root-transaction claim and the new rules are mutually incompatible.
